🧱 Backend module shape

There are exactly two module shapes in this codebase, and which one a feature gets is a project rule, not just an observation:

  • Entity-backed module — a real domain entity (has identity, lifecycle, its own business rules: clubs, users) gets its own module folder with the full 5-piece layout below, including an entity.ts.
  • Value-object module — plain lookup/reference data with no behavior of its own (faculties, categories, and any future "just a labelled row" type) does not get its own module. It's added as a new resource inside the existing master-data module instead (new schema table + repository method + usecase + router sub-object), skipping the entity layer entirely.

Within either shape, dependency direction is strict: router → usecase → repository → (entity, if entity-backed) → Drizzle schema — nothing skips a layer.

modules/clubs/ ├── clubs.router.ts # tRPC router: procedure + Zod DTO → usecase ├── club.entity.ts # Club class: wraps a DB row, getters + toDTO() ├── clubs.repository.ts # ClubsRepository class + singleton export ├── dto/ │ ├── club.dto.ts # base output shape │ ├── get-club-profile.dto.ts # per-usecase input/output, extends base │ └── index.ts # barrel └── usecases/ ├── get-club-profile.usecase.ts └── index.ts

2. Usecase

src/server/api/modules/clubs/usecases/get-club-profile.usecase.ts

export const getClubProfile = async (currentUserId: string): Promise<GetClubProfileOutputDTO> => {
  const club = await clubsRepository.getByUserId(currentUserId);
  if (!club) throw notFound("Club profile not found");

  const user = await usersRepository.getById(currentUserId);
  if (!user) throw internalError({ reason: "Club exists but owning user could not be found", userId: currentUserId });

  return { ...club.toDTO(), email: user.email, role: user.role };
};

Plain exported async functions (not classes) — no DI container, repositories imported directly. Usecases own all domain error decisions; repositories only ever throw generic internalError.

3. Repository

src/server/api/modules/clubs/clubs.repository.ts

class ClubsRepository implements IClubsRepository {
  async create(req: CreateClubParams, client: DbClient = db): Promise<string> {
    const id = randomUUID();
    const res = await client.insert(clubs).values({ ...req, id }).returning({ id: clubs.id }).catch(wrapRepoError);
    return res[0]!.id;
  }
  // getById / getByUserId delegate to a shared private getOneByFilter(filter: SQL)
}
export const clubsRepository = new ClubsRepository();
  • Every method takes an optional client: DbClient = db so it runs standalone or inside unitOfWork.run().
  • Every Drizzle call ends in .catch(wrapRepoError) — the only place raw driver errors are caught.
  • Filter-by-X public methods (getById, updateById, deleteById) are thin wrappers around shared private *ByFilter helpers.
  • Reads use db.query.<table>.findFirst/findMany; writes use the query builder (db.insert/update/delete).

4. Entity

src/server/api/modules/clubs/club.entity.ts

export class Club {
  private constructor(private row: ClubRow) {}
  static toEntity(row: ClubRow): Club { return new Club(row); }
  get id() { return this.row.id; }
  // ... one getter per column
  toDTO(): ClubOutputDTO { return { ...this.row }; }
}

Repositories never return raw Drizzle rows — always Entity | null / Entity[]. Private-constructor wrapper classes, no ORM decorators.

Simpler module without an entity layer — master-data

Read-only faculties/categories lookup skips entities entirely: the repository returns the raw Drizzle $inferSelect row type directly and the usecase just passes it through (master-data.repository.ts:6-7, get-all-categories.usecase.ts:4-6). Use an entity layer only when a module needs derived getters/mapping.

🚨 Error handling

src/server/errors.ts — factory functions, not thrown classes:

export const notFound = (message = "Resource not found") => new TRPCError({ code: "NOT_FOUND", message });
export const internalError = (cause?: unknown) => new TRPCError({ code: "INTERNAL_SERVER_ERROR", message: GENERIC_MESSAGE, cause });
export const wrapRepoError = (e: unknown): never => { throw internalError(e); };

Two-stage safety net:

  1. Repositories .catch(wrapRepoError) on every DB call → wraps into internalError(cause).
  2. errorHandlingMiddleware catches any INTERNAL_SERVER_ERROR result, logs result.error.cause ?? result.error server-side, and re-throws a fresh internalError() with no cause — raw stack traces/SQL errors never reach the client.

Usecases throw notFound/conflict/unauthorized/validationError directly for expected domain failures — those pass through untouched.

🗄️ Data access

src/server/db/index.ts — singleton postgres-js connection, cached on globalThis outside production to survive Next.js dev HMR:

const conn = globalForDb.conn ?? postgres(env.DATABASE_URL);
if (env.NODE_ENV !== "production") globalForDb.conn = conn;
export const db = drizzle(conn, { schema });
export type DbClient = typeof db | PostgresJsTransaction<typeof schema, ExtractTablesWithRelations<typeof schema>>;

src/server/db/unit-of-work.ts — transaction abstraction repositories use for atomic multi-table writes:

export interface UnitOfWork { run<T>(fn: (client: DbClient) => Promise<T>): Promise<T>; }
class DrizzleUnitOfWork implements UnitOfWork {
  run<T>(fn: (client: DbClient) => Promise<T>): Promise<T> { return db.transaction(fn); }
}

No usecase currently uses this yet (all existing usecases are single-repository reads) — the plumbing is in place for when one needs it.

Illustrative example — not real code in the repo yet

A usecase that must create a club and attach its categories atomically (both DB writes commit or both roll back together), then send a welcome email after the transaction succeeds so a failed send never undoes the writes:

export const registerClub = async (input: RegisterClubInputDTO, userId: string) => {
  const clubId = await unitOfWork.run(async (client) => {
    const id = await clubsRepository.create({ userId, name: input.name }, client);
    await clubCategoriesRepository.attach(id, input.categoryIds, client);
    return id;
    // if attach() throws, create()'s insert is rolled back too — both ran on `client`
  });

  await sendMail({ to: input.contactEmail, subject: "Club registered", text: "..." });
  return clubId;
};

The rule this demonstrates: every repository call inside the callback must be passed the same client (not the module-level db) — that's what makes them one transaction. Anything that shouldn't roll back with the DB (email, R2 upload) happens outside the unitOfWork.run() block, after it resolves.

Schema — src/server/db/schema/

One file per table, plus relations.ts (all relations() calls in one place) and index.ts (barrel, imported as import * as schema).

// clubs.ts
export const clubs = pgTable("clubs", {
  id: uuid("id").primaryKey().default(sql`gen_random_uuid()`),
  userId: text("user_id").notNull().unique().references(() => user.id),
  imageUrls: text("image_urls").array().default([]).notNull(),
  contacts: jsonb("contacts").$type<{ instagram?: string; facebook?: string }>(),
  createdAt: timestamp("created_at", { withTimezone: true }).defaultNow().notNull(),
  updatedAt: timestamp("updated_at", { withTimezone: true }).defaultNow().$onUpdate(() => new Date()).notNull(),
});

Conventions: uuid PK + gen_random_uuid() for app-owned entities; text PK for better-auth-owned tables (matches better-auth's own ID format); smallserial PK for small lookup tables; every table has timestamptz created_at/updated_at with $onUpdate; junction tables use a composite primary key, not a surrogate id.

Migrations: drizzle-kit generates SQL into /drizzle (currently 0000–0006). Config: drizzle.config.ts.

🔗 External integrations — src/server/services/

The single place third-party/external-service clients live — anything that isn't the app's own Postgres database goes here, not inside a feature module. Currently two:

const client = new S3Client({ region: "auto", endpoint: env.R2_ENDPOINT, credentials: { ... } });

  • A single module-level client instance (new S3Client(...), new Resend(...)), configured entirely from @/config/env — never instantiated per-call.
  • Plain exported async functions, not a class — usecases import the function directly (import { uploadImage } from "@/server/services/r2"), same import style as a repository.
  • Errors are caught and re-thrown as a generic Error with a safe user-facing message (mailer.ts:41-45) — the raw provider error is logged but not propagated, mirroring how wrapRepoError hides raw DB errors from callers.

Adding a new integration (e.g. push notifications) follows the same pattern: new file here, its own env vars in @/config/env, one module-level client, plain exported functions — called from a usecase like any other dependency. It does not get a dto/, entity.ts, or router of its own; those only exist for modules/<feature>/.

🧭 Where to add what

Add a new endpoint to an existing module (e.g. clubs.updateProfile)

  1. DTO — add dto/update-profile.dto.ts with input/output schemas (extend the module's base schema if shapes overlap); export from dto/index.ts.
  2. Usecase — add usecases/update-profile.usecase.ts, an exported async function calling the repository and throwing domain errors from @/server/errors; export from usecases/index.ts.
  3. Repository method — add to <feature>.repository.ts (+ its interface) following the client: DbClient = db + .catch(wrapRepoError) pattern.
  4. Router — add the procedure to <feature>.router.ts: pick public/protected/admin, wire .input()/.output(), call the usecase.
  5. Router is already registered in root.ts if the module exists — nothing else to wire.

Add a brand-new module (e.g. events)

  1. Create src/server/api/modules/events/ with the same 4 pieces as clubs (skip the entity if there's no derived logic, like master-data).
  2. New tables: add src/server/db/schema/events.ts, export from schema/index.ts, add relations to relations.ts, run yarn db:generate then yarn db:migrate.
  3. Register in src/server/api/root.ts: add events: eventsRouter to appRouter.
  4. Consume via api.events.xyz() (Server Component, @/trpc/server) or api.events.xyz.useQuery() (Client Component, @/trpc/react) — types flow automatically.
Before either is usable end-to-end over HTTP

The missing src/app/api/trpc/[trpc]/route.ts handler (see Gaps found) needs to exist first — without it, no procedure is reachable from Client Components, only from Server Components via the RSC caller.
